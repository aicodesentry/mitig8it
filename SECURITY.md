# Security policy

## Reporting a vulnerability

Email **support@mitig8it.com**. Do not open a public issue.

Include what you need to include for someone else to see it: the component, what you did, what
happened, and what you expected. A proof of concept helps and is not required. If you would like a
reply encrypted, say so and include your key.

## What we will do, stated honestly

This is a small project. Triage is best effort, not a contractual commitment, and there is no
on-call rotation behind this address.

- We aim to acknowledge a report within three working days.
- We aim to tell you within ten working days whether we think it is a vulnerability, and if so
  roughly when we expect to fix it.
- We will tell you when the fix ships, and we will credit you in the release notes unless you ask
  us not to.

If a deadline passes without a word from us, send a reminder. That has been the failure mode
before and it will be again.

There is no bug bounty and no payment.

## In scope

- The GitHub App and the services behind it: the API service, the github service, the analysis
  service, the remediation service and the sandbox broker.
- The GitHub Action in `action/`, including the image it builds and what the orchestrator does
  with the workflow's token.
- The web application at mitig8it.com and its authentication, session and access-control paths.
- Anything that lets one installation read or affect another installation's data.
- Anything that lets repository content influence what the analysis or repair pipeline executes.
  The adversarial fixtures in `benchmarks/remediation/fixtures/` are the shape of this attack and
  a bypass of the controls they test is a real finding.
- Anything that causes the App to write to a repository. It holds no write access to code and no
  code path exists that would commit, push or merge. A path that gets around that is the most
  serious report we could receive.
- Secrets or tokens reaching a log, an error message, a trace, an evidence record or a review
  comment.

## Out of scope

- Findings the scanner misses, and findings it reports wrongly. Those are real defects and we want
  them, but they are product quality rather than vulnerabilities: open an issue with the false
  positive form or the feature form.
- Reports generated by an automated scanner with no demonstrated impact, including missing
  hardening headers, a version number in a banner, and TLS configuration ratings.
- Denial of service through volume.
- Social engineering of anyone involved in the project, and physical attacks.
- Vulnerabilities in a third-party dependency with no path to exploiting them here. Report those
  upstream; tell us as well if the path here is real.
- Anything requiring an attacker who already controls the machine the code runs on.

## What we do not claim

Read this before you decide whether something is a finding.

Repair verification runs in a development sandbox, not an isolated one. Every candidate the
product has produced is labelled `development_unverified`, in the App and in the Action alike.
Repository code executes as ordinary subprocesses with no network, kernel or filesystem isolation.
This is written on every review, in `action/README.md`, and in
`docs/architecture/security-guardrails.md`. It is a known limitation, not a vulnerability. The
isolated job that fixes it is on the roadmap: [ROADMAP.md](ROADMAP.md).

The single-instance development deployment must only be enabled on repositories whose contents the
operator controls, for the same reason.

## Disclosure

Please give us ninety days before publishing, or less if we have shipped a fix and said so. If we
have gone quiet on you, publish. Silence from us is not a reason for you to stay silent.
