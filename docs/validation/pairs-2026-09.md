# Why a pair that exists does not verify, September 2026

`docs/validation/vulnerable-corpus-2026-09.md` ended three rounds of widening the template's
reach with the same sentence each time: the patch count moved and the end-to-end count did not.
After the path containment work it stood at 82 template patches, 40 service proofs, 26 findings
with both halves, and 8 verified. `docs/architecture/known-debt.md` named the next measurement
rather than the next feature: **why does a pair that exists not verify.**

This is that measurement, and then what it showed being fixed.

## How it was measured

`scripts/replay/replay.py --pairs` reads the findings out of the 23 snapshot runs and joins them
back to the same pinned trees, so one scan serves every run of it. For each finding it calls the
engine's own pieces: `static_gate` decides whether the finding is attempted, `generate_proof` and
`generate_template` decide the two halves, and a finding that has both gets a real
`build_patch_bundle` and a real `Verifier` run over the local sandbox. Nothing is
re-implemented, so a pair measured here is the pair the engine would have built.

What it adds is that **the proof's outcome on the original tree and on the patched tree are
recorded separately**, with each one's exit code, its output tail, the verifier's reason and the
run's limitations. A pair verifies only when its proof fails on the original tree and passes on
the patched one. Every other combination is a distinct defect, and collapsing them into one
`verified: false` is what hid all of this.

Two things about the setup are worth stating, because they change the numbers. The snapshot a
pair runs against is not the whole tree: the service accepts 500 files and these trees are far
larger, so the budget is spent nearest the finding first, after the affected file and the root
manifests. And the sandbox's own `python3` and `node` come off `PATH`, so the measurement was run
with a clean interpreter whose `site-packages` is empty. A host interpreter full of packages lets
a module under test import a real dependency the production sandbox would never have had, and the
first run of this measurement did exactly that: pygoat's `introduction/views.py` imported the
harness runner's own `requests` and died inside it.

The numbers below therefore differ slightly from the section they follow on: 75 template patches
here against 82 there, and 35 proofs against 40. The corpus and the findings are identical; the
snapshot each repair sees is not. Both columns of every table on this page were measured with
this one instrument over this one cache, so the comparison within the page is exact.

## The causes, counted

| Cause | Count |
| --- | ---: |
| The file is one policy will not change, so the patch is refused after both halves are built | 10 |
| The module's import closure reaches a package the sandbox does not have | 5 |
| The module's import closure reaches TypeScript syntax the stripper refuses | 2 |
| The proof drives a framework view with a value where a request object belongs | 1 |
| **Total** | **18** |

Three of the five package failures are ES modules and two are CommonJS, which is worth
separating because the harness fakes reached only CommonJS at the time. It did not matter here:
the packages those three modules want are `js-yaml`, `diff` and a scoped internal one, and none
of them is faked either way.

**What is not in the table is the result.** Not one of the eighteen fails on an assertion the
proof makes about behaviour. Not one is a payload the original code already rejects, a repair
that changed a return value, a handler called with a wrong argument list, a module that starts a
server at import, or a sandbox limit. Seventeen of the eighteen never reached the proof's first
assertion, and the eighteenth reached it holding the wrong kind of object. The proof side's
problem, on this corpus, is not what the proofs assert. It is getting the module to load and the
file to be one the service is allowed to touch.

## What was fixed

In order of count.

**A file policy will not change is refused before either generator runs.** `path_forbidden` was
asked inside `build_patch_bundle`, after a template and a proof had both been produced. It is now
asked in the engine's own skip list, beside the unsupported family and the missing source, and
the finding is reported as `protected_path`. This converts no pair; it stops ten from being
counted as pairs, which is the point. Across the whole corpus 31 findings are now skipped there.

**Loadability is decided over the whole closure a load pulls in.** The check read the subject
file and nothing else. It now walks every static `import` and every `require` whose statement
begins at column 0, following relative specifiers the snapshot carries, and refuses with the
module that caused the failure named: `dependency_not_available_in_sandbox:<package>`, or
`typescript_syntax_not_strippable:<construct>` for a TypeScript file anywhere in the closure. A
`require` inside a function body runs when that function is called, which a proof need never do,
so it is not counted and a module that loads is never refused for one. This converts no pair
either; it turns seven proofs that could only fail into seven refusals that say why.

**A Python module inside a package gets a package to be relative to.** pygoat's
`introduction/views.py` begins with a relative import of a sibling, and the harness loaded it
under its bare basename, where `__package__` is empty. It is now loaded under its dotted name
with each intervening directory registered as a synthetic package, `__init__` deliberately not
executed.

**A Python auto-stub can be inherited from.** With the relative import resolved, the load reached
`class NewUserForm(UserCreationForm)`, and the stub for the package Django lives in was an
object, which Python called as a metaclass with a name, bases and a namespace. It is a class now.

**A view whose input is a framework request is refused rather than called with a string.** With
the module loading, the pygoat proof failed on a real assertion, on both trees: a parameter whose
body reads `.method`, `.POST` or `.user` off it is a request object, and there is no fake Django
request to supply. The finding refuses as `request_object_not_constructible`.

**The harness fakes are served to the ES module loader.** `contracts/test-harness-v1.md` recorded
as a ceiling that the fakes were injected through the CommonJS loader only, so a module written
with `import`/`export` got the real `express` or `pg` and failed to load. The
`module.registerHooks` pair that already resolves TypeScript now also resolves a faked specifier,
to a synthetic module that re-exports the live fake as the default and under every name the fake
carries. **On this corpus it converted no pair**, because the three ES module proofs that fail
here fail on `js-yaml`, `diff` and a scoped internal package, none of which is faked. It removes
the ceiling rather than the count, and the contract says so.

### What was refused, and why

**Extending the harness fakes to cover the unfaked requires.** The rule for this round was to
fake a module that appears at least twice among the eighteen, in the style of the existing fakes,
stdlib-free and side-effect-free. Reading the closures says that no such list exists. `dvna`'s
`server.js` reaches fourteen packages, among them `sequelize`, `passport`, `libxmljs` and
`mathjs`; `nodejs-goof`'s `app.js` reaches twenty-five, among them `mongoose`, `typeorm`,
`marked` and three template engines; every one of juice-shop's reaches between eleven and
fifty-six. The overlap between those two is `body-parser`, `express-session`,
`express-fileupload` and `morgan`, and faking all four leaves one module failing on `sequelize`
and the other on `mongoose`. **The unfaked-require cause is not a short tail of
middleware names; it is the whole dependency closure of an application's entry module,** and the
only honest ways to close it are to install the dependencies in the sandbox or to vendor
`node_modules` into the snapshot. Inventing behaviour for an ORM inside a 32 KB harness is not
one of them, because a proof that asserts against an invented `sequelize` asserts nothing.

**Guarding side effects at import: a flag that stubs `listen`, timers and process signals.** Not
one of the eighteen fails on a side effect at import. The `express` fake's `listen` is already a
no-op, `h.run` ends the process when the body settles so a pending timer cannot hold it, and no
pair in the corpus reaches a module that binds a port or opens a connection at load. Adding the
flag would be code with no measurement behind it.

**Asserting the benign case on the sink recording rather than on the return value.** Not one of
the eighteen fails on its benign case. The path-containment proofs already accept a throw, a
callback error or a 4xx as the refusal and already assert containment through `h.fs.reads` rather
than through what was returned. Three of the eighteen are path findings, and all three fail at
`h.load`.

**Following relative imports the snapshot does not carry.** The snapshot is a budgeted slice of
the tree, so a file missing from it says nothing about the repository. Refusing there would
refuse findings on the harness's own byte budget.

## What this says the next constraint is

For three rounds the binding constraint was the template's reach, and then for one round it was
said to be the proof. This measurement says something narrower than either: **the binding
constraint is the sandbox's inability to load an application module that has dependencies.**

84 findings are refused because the module under test imports something the sandbox has no copy
of. Every one of the eight that verify is a module with no imports at all, or none beyond the
standard library: five Node config objects and three Django settings files. That is not a
coincidence and it is not a property of the `hardcoded_credential` family; it is the only shape
of module a dependency-free sandbox can load.

Closing it is not another refusal to remove. It is a decision about the sandbox: install the
repository's dependencies into the verification workspace, or carry `node_modules` and the
site-packages of the snapshot into it, on a network the checks still cannot reach. Both are
larger than anything this page changed, both carry a real supply-chain question, and neither
should be started without measuring what share of the 84 a dependency install would actually
reach. `docs/architecture/known-debt.md` carries that as the open item.

## With dependencies installed

The section above ends by naming one number as the binding constraint: 84 findings get no proof
because `dependency_not_available_in_sandbox`, and every pair that verifies is a module with no
imports beyond the standard library. It also says what to do about it, which is to measure what
share of the 84 a dependency install would actually reach before deciding anything about the
sandbox.

This is that measurement. It was run on a fresh set of 23 snapshot scans over the same corpus at
the same pinned refs, so its own before column is 81 rather than 84; the scanner's run-to-run
variation moves the finding set by a few rows and nothing here turns on the difference. Both
columns below were taken with one instrument over one cache, so the comparison within this
section is exact.

### How it was measured

`scripts/replay/replay.py --pairs --with-dependencies` installs each repository's dependencies
into its pinned tree, lets the sandbox workspace see them, and runs the same pairs measurement.
Three things about the setup are load-bearing.

**The install is the remediation service's own.** `src/sandbox/dependencies.py` is what runs, so
this measures what `policy.install_dependencies` does rather than a harness approximation of it:
`npm ci --ignore-scripts --no-audit --no-fund` when a lockfile exists and
`npm install --package-lock-only` first when none does, and `pip install --only-binary=:all:`
from `requirements*.txt` or from the project, into a venv beside the tree. Ten minutes per
repository, network only for that step.

**A manifest had never reached the pairs snapshot.** `walk_analysable_files` answers the
scanner's question, and `package.json` is not an analysable extension, so the worker's own
`PAIR_ROOT_FILES` listed names that never arrived. The engine reads a manifest to decide that a
database driver is a real dependency, and with the install on it reads one to decide that a
workspace will have a `node_modules` at all. The instrument now carries the root manifests
whatever their extension, and both columns here were taken after that fix.

**A repository is installed once and every workspace is pointed at it.** A pair materializes the
workspace twice per check and a repository has dozens of pairs, so the local driver reads
`SANDBOX_LOCAL_DEPENDENCY_ROOTS` and links the installed tree in. The service installs per
workspace instead; that isolation is what the measurement gives up in order to be runnable, and
it is the only difference between the two.

### The eight that already verified still verify

This was the regression to look for. The proofs assert **through** the harness fakes, so a
workspace that now carries a real `express` or a real `psycopg` must not hand the module under
test the real one: a fake that is shadowed would turn eight proofs into eight assertions about a
package.

All eight still verify with a `node_modules` and a site-packages present, five NodeGoat
configuration objects and three pygoat Django settings files, unchanged.

**How the harness decides precedence, and why it cannot drift.** It is not a lookup order, it is
an answer given before the real resolver is ever asked. The JavaScript harness replaces
`Module._load` and returns `fakes[name]` before calling Node's own loader at all, and its
`module.registerHooks` `resolve` returns the fake's synthetic `mitig8it-fake:` URL before
`nextResolve`; a `node_modules` beside the module is never consulted for a faked name, under
either loader. The Python harness writes each fake into `sys.modules` before the module is
executed, and `sys.modules` is consulted before any finder on `sys.meta_path`, so an installed
`flask` or `psycopg` is never reached, while `os.system`, `os.popen`, `os.environ` and `open` are
replaced on the real objects, which nothing installed can take back.
`services/remediation-service/tests/test_dependency_installed_verification.py` holds this with a
real package of each faked name installed beside the module under test: `express`, `pg`,
`child_process` and `fs` under both Node loaders, `flask`, `sqlite3`, `psycopg` and `subprocess`
with a site-packages on the path, and one test that the recorders a proof asserts on still fill
up.

### What this decided

**The dependency install was not built into the production sandbox.** The bar set before the
measurement was 20 of the 84 verifying. The answer is 0 of 81. Installing dependencies converts
the refusal reason and not the outcome: 81 findings that said
`dependency_not_available_in_sandbox` become 73 that name a site a proof cannot drive, 7 pairs
that fail at load for other reasons, and 1 with no template. Against that, a production install
is the one step of a verification run that would reach a package registry, over a tree chosen by
whoever opened the pull request, at 1.7 GB per corpus and 50 seconds for the largest repository.
That is a real supply-chain question bought for nothing.

`policy.install_dependencies` exists, defaults false, and is implemented for the development-only
local driver, which is what this measurement runs on.
`services/remediation-service/contracts/repair-v1.md` says so under "Installed dependencies", and
says why the isolated drivers do not have it.

**What the measurement says the constraint actually is.** With loadability removed, the largest
single reason a finding gets no proof is `module_scope_source_not_controllable` at 40 of the 81,
and dicebear alone contributes 29 of them: a secret at module scope in a file the proof cannot
make the module read differently. That is a proof-generation question rather than a sandbox one,
and it is the first thing this page has measured that is neither the template's reach nor the
sandbox's.

```sh
PY=~/.pyenv/versions/3.11.6/bin/python

# the same 23 snapshot scans as above, then both columns over that one cache
PATH=/path/to/empty-venv/bin:$PATH \
  $PY scripts/replay/replay.py --pairs --results scripts/replay/results/*.json --out /tmp/pairs.json
PATH=/path/to/empty-venv/bin:$PATH \

```

`--with-dependencies` writes an install marker beside each cached tree, so a rerun over the same
cache costs no `npm ci`. Deleting `scripts/replay/.cache` removes the installed trees with it.
