# Release notes, 24 September 2026

Eighteen pull requests integrated onto `integration/2026-09-24` from `origin/main`, in
dependency order: 437, 436, 429, 428, 435, 440, 441, 442, 438, 444, 446, 445, 447, 448,
449, 450, 451, 452.

This branch is not a release. It is the first time all eighteen have existed together,
measured together, and passed their suites together. Everything below states what changed
and what it was measured at; the limitations section states what it still does not do.

## The measured numbers

| | Before | After | Where |
| --- | ---: | ---: | --- |
| Precision of posted findings, vulnerable corpus | 0.67 | **0.97** | PR 447 with PR 441 |
| Recall on labelled lines, vulnerable corpus | 0.40 | **0.58** | PR 449 |
| Tier 2 rules, JavaScript, TypeScript, Python, templates | 25 | **130** | PRs 445, 449 |
| Remediation fixtures | 11 | **55** | PRs 446, 447, 449, 450, 452 |
| Candidates produced and sandbox-verified end to end on the corpus | 5 | **8** | PR 450 |

Of the 130 tier 2 rules, 124 post and 6 are quarantined on measured precision. The 55
fixtures are 43 supported repairs, 8 negatives that must be abstained on, and 4
adversarial repositories whose own content tries to steer the agent. All 43 supported
repairs verify under both the reference and the `engine-local` adapter, with no unexpected
failures under either.

The precision figure is the precision of what posts, not of what the scanner produces.
The corpus produced 1819 findings, of which 172 were adjudicated by hand; everything
scored 0.67. Restricting to what posts once the tier 1 quarantine applies leaves 378
findings, 113 adjudicated, 110 true and 3 false, which is the 0.97.

## Product

**One finding and one suggestion per vulnerable line (PR 429).** Both analysis tiers can
prove the same flaw on the same line. GitHub accepts one suggestion per line, so a group
of proven candidates on overlapping lines now publishes one suggestion and the rest say
which comment carries the fix. The candidate that keeps the suggestion is chosen by
coverage, then verification level, then candidate id, so the choice does not depend on
the order candidates arrive in. Internal types are derived once for both tiers, so a
finding from tier 1 and a finding from tier 2 for the same vulnerability group together.

**A scan survives a file it cannot read (PR 437).** One warning-level lexical error in one
file used to discard every result from every file in the batch: test-only PR 135 published
"Security analysis incomplete" with no findings after discarding 97 results from 12 files.
Scanner errors are now classified. A per-file parse problem or resource ceiling becomes an
`analysis_limitations` entry on the run, stated in the check summary and the review
comment, and the other files' findings are kept. Only an unattributable error-level
failure still fails the scan closed, now with the error details in the raised message.

**A large pull request is reviewed, not refused (PR 442).** A pull request over the
200-file cap is reviewed to the cap in deterministic path order with a stated limitation,
instead of failing. Refusing was the one case where a developer got nothing back.

**Tier 1 posts only what it can stand behind (PR 441, PR 447).** The September 2026 replay
read 30 tier 1 findings by hand and found 29 false. Six rules are now quarantined: they
still run and are still counted, but nothing they produce is posted, counted in the check
summary, or handed to remediation. Five come from the replay (`null.pointer.deref`,
`integer.overflow`, `rate_limit.missing`, `authz.missing_function_level`,
`concurrency.shared_state`); the sixth, `path.traversal.user_path`, comes from the
vulnerable corpus at a measured precision of 0.43. Each carries its own
`precision_evidence` string naming the measurement that would let someone re-enable it. A
static check catches the ineffective-lookahead regex shape that caused several of them,
comments are stripped before matching, and a labelled benchmark in
`benchmarks/tier1-precision/` gates every rule change.

**Tier 1 stops reading prose as code (PR 440, PR 449).** Rules that recognize the shape of
executable code no longer run on changelogs, READMEs, licence text or templates. Rules
that recognize committed data, such as a credential literal, still do: a secret pasted
into a README is still a leaked secret.

**Tier 2 covers what it claims to (PR 445, PR 449).** The rule set went from 25 to 130 for
JavaScript, TypeScript, Python and 16 template extensions, every rule written in this
repository after both public rule libraries were found to forbid use in a paid service.
Each rule declares its own posting state next to the pattern whose precision was measured,
and both tiers feed one quarantine set read by one filter. Template files are now fetched
and scanned at all, which is what closed most of the cross-site scripting gap: XSS recall
went from 1 of 32 labels to 26 of 32, path traversal from 2 of 14 to 8 of 14.

**Repairs reach code that is not an Express route (PR 448, PR 450).** All five families
(`sql_parameterization`, `command_arguments`, `path_containment`, `hardcoded_credential`,
`code_injection_eval`) now repair on both JavaScript and Python. The Node harness records
environment reads and records `eval`, `new Function`, the `vm` compile calls and a string
timer without running them. Repair sites are no longer restricted to route handlers: the
site model prefers the enclosing route and falls back to the enclosing function, method or
`exports.name` binding, which took `enclosing_route_not_found` from 123 refusals to 0.

**The evaluation corpus grew from 11 fixtures to 55 (PRs 446, 447, 449, 450, 452).** 43
supported repairs, 8 negatives, 4 adversarial. All 43 supported repairs verify under both
adapters, and both exit 0 with no unexpected failures.

**TypeScript loads and module-scope findings get proofs (PR 452).** The two obstacles left
in front of verified fixes on real code were 52 TypeScript modules the sandbox could not
load and 67 findings at module scope with no function for a proof to drive. TypeScript now
runs on Node's own type stripper (the pinned runtime moves from 20 to 22.23.3, and the
harness resolves the extension-less relative imports, directory indexes and `.js`
specifiers a NodeNext project writes for a `.ts` source, for both CommonJS and ES modules).
A `ModuleScope` site now carries a driver describing how the tainted value enters:
`process.env` or `os.environ`, `process.argv` or `sys.argv`, or a member of a top-level
relative `require`. On the corpus, `enclosing_function_not_found` fell from 67 to 9 and
`module_not_loadable_by_node` from 59 to 0, 126 refusals in total, and the template builds
a patch for 33 findings rather than 30. Verified end to end stayed at 8.

The four benchmark cases the previous branch recorded as one adapter defect turned out to
be four separate proof defects, found by running each fixture's proof against its own
reference: swapped payload sets in the Python traversal proofs, a handler called as a
function, a secret read inside a function the proof never called, and a callback-reporting
helper whose repair threw. The adapter change is the small part: an exhausted script is now
an abstention with a count rather than a runtime error.

**Marketing pages state facts only (PR 428).** The Examples, About and Security pages were
rewritten so every claim is sourced from code or docs. The Security page now lists what the
product reads, what it writes, how a fix is verified, what model calls are made, what data
is kept and what access it holds.

## Trust

**No write access to code (PR 442).** The in-app apply commit path and the merge controller
are removed from api-service, github-service, the proto and the panel. The App needs
Contents read, Pull requests read and write, Checks read and write, and Metadata read. A
fix reaches a branch only through GitHub's own "Commit suggestion" button, under the
developer's identity. There is no apply or merge flag left to set.

**Uninstalling deletes the data (PR 442).** `installation.deleted` marks the installation
and schedules a purge 24 hours later, which a reinstall in the window cancels. The purge
deletes in dependency order across 25 tables in one transaction, inside the row-level
security scope the remediation tables force, and records per-table counts in a single audit
row.

**Every decision about a finding is recorded (PR 436).** Published fixes, applies,
dismissals, suppressions, thread resolutions, re-analysis results and residuals are
appended to `finding_outcomes` with a reason, and rolled up daily into apply, dismiss and
residual rates per installation and per rule, exported as three Prometheus gauges and shown
on the dashboard. A reviewer resolving the bot's thread, or replying "not an issue" to it,
is a decision and is recorded. A commit carrying the app as co-author is a published
suggestion the developer applied, and one scan of the pushed commits records both the
outcome and the observed apply action.

**Verification in an isolated Cloud Run job (PR 438).** A third sandbox driver,
`SANDBOX_DRIVER=cloud_run_job`, runs each half of each check pair in its own job container
under a separate unprivileged user, and reports `isolated_job` evidence only when the
task's own probes measured the metadata server, a public address and DNS as unreachable
immediately before the check ran. It is off by default and nothing has been applied to a
project.

**Precision and recall measured on real vulnerable code (PR 447, PR 449).** 171 labelled
vulnerabilities across 23 repositories at pinned refs, run through both tiers. This is what
produced the 0.67 to 0.97 precision figure and the 0.40 to 0.58 recall figure, and what
justified the sixth quarantine.

**Real pull requests replayed (PR 440).** 165 merged pull requests from 11 public
repositories through the analysis and remediation pipeline, with four robustness bugs fixed
and every crash, timeout and limitation triaged.

**A production readiness checklist (PR 435).** `docs/production-readiness.md` states the bar,
the current state and the evidence for each item, across correctness, trust, operations and
distribution.

## Operations

**Metrics reach a dashboard (PR 444).** Analysis runs by trigger, completions, failures by a
closed set of reasons, duration by outcome, findings posted by severity, queue depth, oldest
pending age, seconds since last start, a derived stalled gauge, and remediation jobs by
terminal state. Every series exists at zero from the first scrape. A loopback-only listener
on 127.0.0.1:9091 serves a Cloud Run Managed Prometheus sidecar on the API with a 30 second
scrape.

**Two alerts that can fire (PR 444).** Reviews failing (failures over starts above 0.3 in 15
minutes with at least 3 starts) and reviews stalled (the derived gauge, plus an absent-series
condition in Cloud Monitoring so silence pages too). Lease reclaim stays a warning. Eleven
rules that queried metrics nothing ever emitted were deleted.

**Correlated logs (PR 444).** Delivery id, analysis run id, job id and correlation id flow
through AsyncLocalStorage in the Node services and contextvars in the Python analysis
service, over HTTP headers, gRPC metadata and the queue boundary via a new
`analysis_runs.delivery_id` column. Every line is one JSON object with severity and message.

**First review latency (PR 444).** `--min-instances 1` on the API behind a workflow input,
with a non-blocking warm-up on start that opens the pool, pings the github and analysis
services and pre-mints identity tokens.

**A staging environment (PR 444).** All five deploy workflows take an environment input
mapping to `-staging` service and secret names, and `deploy-staging.yml` runs them on push
to a `staging` branch. No cloud resources are created by the branch.

**Migrations.** Six new migrations apply in order with no duplicate numbers: 0023
`finding_outcomes` and 0024 `quality_metrics_daily` (PR 436), 0025
`analysis_run_limitations` (PR 437), 0026 `observed_apply_actions` and 0027
`installation_purge` (PR 442), 0028 `analysis_run_delivery_correlation` (PR 444).

## Distribution

**Run the review as a GitHub Action (PR 451).** `uses: aicodesentry/mitig8it/action@main`
runs in the repository's own runner with the workflow token. No App install, permissions
declared in YAML, removable by deleting the workflow. The action reads its own grant and
refuses to start when `contents: write` is present or when the permissions object is
missing, because a least-privilege check that fails open is decoration. Nothing leaves the
runner by default; the only host contacted is the GitHub API. With `model-api-key`,
redacted snippets go to that provider; without it, triage is off and template fixes still
run. Analysis runs in process through the service's own entry point and the check run,
inline comments and suggestion blocks are the github-service's own functions, so the
Action inherits the posting policy rather than reimplementing it. The one extraction is an
identity provider separating the App's four coupling points from the publishing code; the
App path is unchanged.

**Public dogfood (PR 451).** `.github/workflows/mitig8it-self-review.yml` runs the action on
this repository's own pull requests.

## Integration fixes

Four checks failed on the integration itself rather than on any one pull request, because
the eighteen were first measured together here. The offline remediation fixture gate still
set up Node 20 after PR 452 moved the sandbox runtime to 22.23.3, so the test harness's
type stripper and module hooks were missing and three engine-local pipeline cases read a
rejected flag set as a candidate that could not prove itself; the gate now takes its
version from `ARG NODE_VERSION` in the service Dockerfile, and the local driver names the
missing feature instead of failing the candidate. PR 438's `deletion_protection` needs
google provider 6, so the remediation module moved from `~> 5.0` to `~> 6.0`, which the
whole module validates against unchanged. One shellcheck finding in
`deploy-api-cloudrun.yml` was the only thing PR 451's actionlint job had to say about the
merged tree. And the Action sent a 40-character Git object ID as `manifest_digest`, which
the github-service envelope validator rejects, so every run that produced a fix died after
posting its review and its check run; the orchestrator now computes the digest the way
`manifestDigestFor` does in the App.

**Per-repository path exclusion.** The dogfood run posted 34 findings on
`benchmarks/remediation/fixtures`, which is code that is supposed to be insecure. A
repository now configures Mitig8it with a `.mitig8it.yml` at its root, with one key,
`exclude`, a list of globs. An excluded path is never analysed: it is dropped from the
changed-file list before any content is fetched, so no finding, comment or fix can come
from it, and it is not counted towards the file cap. The check summary states
`N files excluded by .mitig8it.yml`, because silence about a directory should not be
mistaken for a clean bill of health. The App reads the file in
`services/api-service/src/services/repositoryConfig.js` and the Action in
`action/orchestrator/repo_config.py`; the glob dialect and the parse rules are stated once
in `contracts/repository-configuration-v1.json`, and both sides are tested against those
cases rather than against each other. This repository's own file excludes `benchmarks/**`,
`docs/validation/**` and the action's recorded test fixtures: all of it measurement input,
including the labelled vulnerable snippets the tier 1 and tier 2 precision case files quote
verbatim and the write-ups that quote them again. Documented in
[Repository Configuration](../getting-started/configuration.md).

## Owner steps after merge, in order

1. **Subscribe the App to two events.** Enable **Pull request review thread** and **Pull
   request review comment** on the GitHub App. Without them, thread resolutions and reply
   dismissals never reach the outcome log, and the dismiss rate under-reports. See
   `docs/getting-started/github-app.md`.

2. **Set Contents to read-only.** In the App's permissions, set Repository permissions >
   Contents to **Read-only**, leaving Pull requests and Checks at Read and write and
   Metadata at Read-only. GitHub applies a permission reduction automatically in most
   cases. An installation that has not yet accepted keeps the wider grant and behaves
   identically, because nothing uses it. See `docs/getting-started/github-app.md`.

3. **Work the sandbox runbook, if the isolated job level is wanted.** Six ordered steps in
   `docs/runbooks/sandbox-cloud-run-job.md`: apply the Terraform, build and push the first
   job image, compute the digest and point the job at it, smoke test one execution and check
   the probes came back denied, flip the driver, confirm one real verification. Step 4 is the
   one that decides the outcome: it says whether Cloud Run permits the unprivileged user
   namespace the metadata-server denial depends on. Do not flip the driver before it passes.

4. **Do the observability one-time setup.** Create the `codesentry-gmp-config` secret from
   `infrastructure/monitoring/runmonitoring.yaml`, grant the Cloud Run runtime service
   account `secretmanager.secretAccessor` on it and `monitoring.metricWriter` on the
   project, then `terraform apply` in `infrastructure/monitoring` to create the email
   notification channel and the alert policies. Confirm the channel from the mail Google
   sends, because it does not deliver until confirmed. See `docs/runbooks/observability.md`.

5. **Do the staging one-time setup.** Create a staging database (a Neon branch from
   production is preferable, never the production connection string), create a **separate**
   staging GitHub App installed only on test repositories, and store freshly generated
   secrets rather than copies of production. See `docs/deployment/staging.md`.

6. **Rotate the model key.** `codesentry-gemini-api-key` in Secret Manager backs tier 3
   triage. Rotation is pending and has not been performed.

## Known limitations

Stated as the pull requests state them. Nothing here is a plan; it is what the branch does
not do.

### Verification

- Every candidate ever produced, in fixtures and on live pull requests, is
  `development_unverified`. No result in this branch satisfies an isolation gate.
- The Cloud Run job driver (PR 438) is off by default and has not been applied to a
  project. Its `isolated_job` level is weaker than `independent_sandbox` and claims only
  what its probes measured. It cannot guarantee: that the network stayed unreachable for
  the check's whole lifetime (the probes are one measurement at one moment from one
  process, and do not enumerate every address a check might try); a read-only root
  filesystem (a Cloud Run container has a writable overlay, so a check can write over the
  interpreters on its own `PATH`); a gVisor runtime class (the boundary is the ordinary
  container boundary, so a container escape is a container escape); or the availability of
  the unprivileged user namespace, which is the only thing denying the link-local metadata
  server. The entrypoint feature-detects it and reports `applied` or `unavailable`, and
  when it is unavailable the driver refuses every result rather than claiming the level.
- The Cloud Run job image was exercised on Docker Desktop, which blocks user namespaces, so
  only the designed refusal path fired. `terraform fmt -check` is clean; validate and plan
  need Terraform 1.6, which was not installed locally (PRs 438, 444).
- The Kubernetes and gVisor driver exists and is rendered, but nothing has been applied to a
  cluster and neither attestation flag is justified by this work.

### Detection

- There is no false-negative corpus for the tiers themselves beyond the vulnerable corpus,
  so a finding the scanner does not raise on code outside that corpus is still invisible.
- PR 445 widened tier 2 to 116 rules on an argument, not a measurement: 87 of them post
  because they matched nothing on clean code and are sink-only matches with a clear
  taxonomy. Over 165 real pull requests, exactly one of the 91 new rules fired, six times,
  all false, and it was narrowed.
- Tier 2 produced zero findings over 816 real files in the replay (PR 440), and no finding
  mapped to a repairable family, so the remediation engine never ran on real replay input.
- Reach and posted reach are different numbers (PR 449). Of the 26 cross-site scripting
  labels reached, 8 are reached only by a rule quarantined on measurement, so 18 of 32 reach
  a reviewer; for path traversal it is 7 of 14.
- Six rules are quarantined on measurement and post nothing:
  `cwe-79.js-html-string-interpolated` (678 findings, precision 0.47, cannot see a value
  already wrapped in an escaper), `cwe-79.tpl-unescaping-filter` (0.70 over ten adjudicated,
  every false one `{{ logo|safe }}` on markup the application itself builds),
  `cwe-79.js-dangerously-set-dynamic`, `cwe-1275.js-cookie-samesite-none`,
  `cwe-79.py-jinja-autoescape-off` and `cwe-489.py-debug-constant-true`. Separating their
  false positives from real injections needs a data-flow answer the AST pattern engine does
  not give.
- Three rules the corpus could not decide, all below the three adjudicated findings the
  policy requires: `xss.unsafe_html_render` (16 findings, 2 adjudicated, 0.50),
  `auth.bypass.missing_check` (8 findings, 1 adjudicated, 0.00) and
  `opengrep.cwe-798.hardcoded-secret-js` (5 findings, 2 adjudicated, 0.50).
- `opengrep.cwe-489.py-debug-constant-true` has two measured hits, both real `DEBUG = True`
  in a Django settings module, so its quarantine reason is known to be wrong. It still
  cannot come back, because the policy asks for three.
- None of the six quarantined tier 1 rules was re-enabled. Mechanical regex repairs were
  made, but only `integer.overflow` clears all its quoted samples, and what remains is still
  "the line contains parseInt" with no true positive anywhere in the corpus. Each needs a
  rule design, not a regex repair.
- The tier 1 comment model has known gaps. All of them cause false negatives, not false
  positives. String blanking is per rule and opt-in, because default-on blanking destroys
  rules whose signal lives in literals.
- A tier 1 rule reports at most one finding per rule per file, at the first match. Nine of
  the 18 labels found in the file but not on the line are this. It caps recall on any file
  with more than one instance of the same defect.
- Tier 1 exceeds the orchestrator's 30 second budget on large payloads. 200 files of 75 kB
  measured 50 s; the worst legal payload, 300 files at 200 kB, is about 200 s. The per-file
  budget stops the pass and reports what it did not reach rather than blowing the deadline.
- Command injection built on one line and run on the next is not matched (7 of 11 labels
  found); every miss needs one hop of data flow the AST pattern engine does not provide.
- Template rules run in the scanner's generic mode, because the html parser claims only
  `.html` and `.htm` and emits partial-parse warnings on server tags, and the vue parser
  returns nothing on a standard component.
- Pug's `!= expr` is not matched: in generic mode it is indistinguishable from the
  inequality operator in the inline JavaScript those files carry.
- `.erb`, `.svelte` and `.dust` have rules and no corpus repository uses them, so those
  rules remain unmeasured.
- Still missed after PR 449: three NodeGoat labels are plain `{{ }}` in swig templates whose
  autoescape is disabled in a different file; `anxolerd/dvpwa`'s
  `setup_jinja(..., autoescape=False)` is deliberately not matched; four DSVW labels build
  HTML with no interpolation on the labelled line.
- A rule-level `metavariable-regex` silently drops every pattern that does not bind the
  metavariable, which had deleted three of six branches of an existing rule with no test
  failure.
- Pre-existing tier 2 rules in `javascript.yml` and `python.yml` declare no `internal_type`,
  so they pass their check id through as the type and form a category of one that nothing
  else can group with. The metadata test forbids this for the coverage rules only.
- Three corpus true positives could not be reproduced in isolation and were left out of the
  benchmark rather than adjusted.
- The corpus has no CWE-798 fix commit and no Java, Go, Ruby, PHP or C#, so recall for those
  rules is unmeasured.
- Labels in the corpus are sinks, so the recall figure is recall over the vulnerabilities a
  pattern scanner could in principle find, not over the vulnerabilities the applications
  have. Every missing-control vulnerability is absent from the denominator.
- A snapshot is not a pull request: whole files are analysed rather than changed lines, so
  the precision figure is a property of the rule set rather than of a reviewer's inbox.
- Tier 3 never ran in any measurement here (no model key, `LLM_TRIAGE_ENABLED=false`), so
  every count is pre-triage.
- Hand-read samples of 30 and of 40 of 1687 are enough to separate 0.02 from 0.97 and are not
  strong enough to separate 0.9 from 0.95.

### Repair and the corpus

- 55 of the 120 fixtures the release manifest requires, all authored in this repository, with
  no external review signatures, no trust root and no cryptographic signature verifier.
  `evaluate.py --suite release` exits 2 by design and no family reaches the 20 supported
  cases the manifest wants.
- Reference-adapter numbers measure the authored answer, not the agent. The `engine-local`
  adapter measures pipeline integrity, not repair quality. The two must never be reported as
  one number, and nothing in the seed measures the deployed system.
- Three rounds of removing an obstacle have not moved the reach. PR 450 took
  `enclosing_route_not_found` from 123 refusals to 0; PR 452 took
  `enclosing_function_not_found` from 67 to 9 and `module_not_loadable_by_node` from 59 to
  0. Verified end to end was 8 before both and is 8 after both. 60 of the 67 module-scope
  findings run their sink at import from a call no test can set, which is refused correctly,
  and the nine TypeScript proofs that existed before were written against modules the
  sandbox could never load. The remaining refusals are now specific enough to work on one at
  a time: `path_module_not_required` 65, `path_join_not_found_in_scope` 27 and
  `function_parameters_not_plain_names` 23.
- The sandbox's built-in fakes reach only CommonJS modules, so an ES module TypeScript proof
  fails safely rather than passing. An interface imported as a value binding survives type
  stripping and fails to load.
- `module_not_loadable_by_node` still fires for JSX and TSX. Enum, namespace and parameter
  properties are refused as `typescript_syntax_not_strippable:<construct>`. On the corpus all
  88 TypeScript findings across 73 files are strippable.
- Of the six new site-shape fixtures, five produce a template patch and a proof matching the
  reference byte for byte; the class-method one declines the proof together with the patch.
- One site, `appsecco/dvna` `server.js`, still does not verify: its proof must load a module
  that requires `express` and the snapshot has no `node_modules`.
- `new Function`, `vm.Script` and the `vm.runIn*` calls are refused by a static gate as
  `dynamic_code_unsupported`, because they compile a program and no data parser stands in for
  that.
- The proof-dependency exemption covers only the modules the Python harness fakes.
  Application patches are unchanged, so a driver the sandbox fakes is still a dependency a
  deployment must install.
- The `spawn` shell refusal narrows only to commands whose literal text carries pipeline or
  redirection metacharacters.
- Five Python SQL findings raise `AttributeError` in the direct-generator measurement because
  that measurement's harness stub does not implement `Snapshot.paths`. The count is identical
  in both runs, so the comparison is unaffected, and the engine itself passes a real snapshot.
- 184 of 245 attempts stop at the refusing provider by design, so nothing here measures the
  model path.
- Only five families are repaired (`sql_parameterization`, `command_arguments`,
  `path_containment`, `hardcoded_credential`, `code_injection_eval`). Everything else is
  reported per finding as `unsupported_rule_family`.
- Repair memory rows are written and never read or promoted. Retention and deletion jobs do
  not exist.
- No online quality metric is collected from live runs, so live precision and abstention
  rates are unknown. No live installation has yet produced enough outcomes to read the apply,
  dismiss and residual rates, and a rate with no denominator is not exported at all rather
  than exported as zero.

### Operations and trust

- Metrics are connected; traces are not. No deploy workflow sets an OTLP endpoint, so spans
  go nowhere, and the github and analysis services are unscraped.
- Alert policies are not yet scoped by service name, so a staging failure would page the
  owner. The "reviews failing" alert treats no data as OK by design, because "nothing ran" is
  the other alert's question.
- `--min-instances 1` costs about $50 a month at the current shape.
- The application connects as a database role with `BYPASSRLS`, so the forced row-level
  security policies are defined and never enforced in production.
- The restore reconciliation procedure has never been exercised, so its fencing and outbox
  assumptions are untested. The backup and restore drill is open.
- No runbook has been run end to end by someone other than its author.
- `webhook_deliveries` has no tenant column and is out of scope for the uninstall purge.
- Inline fix publication and feedback are not written to `audit_logs`.
- Merge is removed, not parked. It was exercised live exactly once, on test-only PR 126, and
  never against a repository with branch protection. History rows are retained and no new
  apply or merge action can be created; no flag can bring either back.
- The Security page says the product "never commits or merges on its own" rather than "never
  commits", and does not claim secrets are redacted before model calls. It claims only that
  secret paths are excluded and that keys are stripped from logs.
- Model key rotation is pending.
- Load, chaos and security acceptance testing has not started.
- `proto/requirements.txt` pins grpcio-tools 1.83.1, which would emit generated code newer
  than the analysis service's protobuf runtime. Regeneration was done with 1.71.2 to keep the
  stamp unchanged; aligning the pin is a separate change.
- Test counts fell in api-service, github-service and the frontend when the write paths were
  removed, because those paths carried heavy coverage. They were replaced with guards
  asserting the removed operations no longer exist.

### The Action

- No dashboard, no outcome metrics, no isolated sandbox (the Verified line says development
  grade in the runner), and no suppressions or baselines, so a dismissed finding returns.
- Reviews are posted as comments rather than change requests. `fail-on` carries the blocking
  decision and defaults to none.
- Without `model-api-key`, triage is off and the engine gets an abstaining provider, so only
  template fixes run and the summary says the agent path was disabled. With a key, redacted
  snippets go to that provider.
- The action image could not be built on the authoring machine because Docker's engine did
